# NetDoctor 1주차 설계서

## 1. 목표와 범위

NetDoctor는 네트워크의 여러 구간을 독립적으로 측정하고, 관측값의 조합을 근거로
가능성 높은 병목을 설명한다. 1주차의 목표는 실제 측정이 아니라 **측정 경계와 데이터
계약을 먼저 고정하는 것**이다.

이번 주에 포함되는 항목은 다음과 같다.

- 측정 대상과 반복 횟수 설정
- DNS, TCP, TTFB, 다운로드 처리율, RTT의 조작적 정의
- 평균·중앙값·최솟값·최댓값·표준편차를 담는 데이터 모델
- 측정기·분석기·API·화면 사이의 책임 분리
- CLI 실행 골격과 웹 대시보드 와이어프레임

실제 네트워크 요청, 규칙 기반 판정, 측정 이력 DB는 각각 2~4주차 범위다.

## 2. 강의 내용과의 연결

- 처리율은 명목 대역폭이 아니라 비트가 실제 도착하는 속도다.
- 종단 간 처리율은 가장 느린 병목 링크의 영향을 받는다.
- RTT에는 전파 지연뿐 아니라 처리 지연과 변동하는 큐잉 지연도 포함된다.
- TCP는 응용 데이터를 보내기 전에 연결 설정 핸드셰이크가 필요하다.
- DNS는 계층적·분산형 시스템이며 캐시 유무에 따라 관측 시간이 크게 달라질 수 있다.
- 저장형 영상은 처리율의 영향을 크게 받고, 화상회의는 지연·변동·손실에 더 민감하다.
- 인터넷은 지연이나 처리율을 보장하지 않으므로 단일 측정보다 반복 측정이 적절하다.

## 3. 측정 정의

| 키 | 표시 이름 | 단위 | 시작과 종료 | 주의점 |
|---|---|---:|---|---|
| `dns_ms` | DNS | ms | 이름 조회 호출 직전부터 IP 결과 반환까지 | OS·로컬·재귀 DNS 캐시 영향 기록 |
| `tcp_ms` | TCP 연결 | ms | 이미 얻은 IP에 `connect()`를 호출한 시점부터 성공까지 | DNS와 TLS 시간을 포함하지 않음 |
| `ttfb_ms` | TTFB | ms | 연결된 소켓에 HTTP 요청을 쓰기 시작한 때부터 첫 응답 바이트까지 | TCP·TLS 설정 시간을 포함하지 않는 분리 지표 |
| `download_mbps` | 다운로드 | Mbps | 응답 본문 첫 바이트부터 마지막 바이트까지 | 헤더와 연결 준비 시간 제외, 서버 제한 가능성 명시 |
| `rtt_ms` | RTT | ms | ICMP Echo 요청과 응답의 왕복 | ICMP 차단·우선순위 차이 때문에 실패가 단절을 뜻하지 않음 |

HTTPS TTFB를 측정할 때는 TCP 다음에 TLS 설정 시간이 추가된다. 프로젝트의 핵심 다섯
지표를 섞지 않기 위해 TLS 시간은 내부 보조 지표로 별도 기록하고, `ttfb_ms`에는 넣지
않는다. 사용자 관점의 전체 웹 대기 시간은 이후 `dns + tcp + tls + ttfb` 형태의 파생
지표로 제공할 수 있다.

## 4. 반복과 통계 정책

- 각 지표를 한 진단에서 5~10회 측정한다.
- 반복 사이에는 기본 0.25초 간격을 둔다.
- 평균, 중앙값, 최솟값, 최댓값, 모집단 표준편차를 저장한다.
- 대표값은 순간적인 이상치에 덜 민감한 중앙값으로 표시한다.
- 원본 표본도 버리지 않고 결과에 저장해 변동과 이상치를 확인할 수 있게 한다.
- 일부 표본 실패와 전체 실패를 구분한다. 실패를 0ms로 저장하지 않는다.

측정 순서는 한 지표를 연속해서 모두 재는 방식보다 DNS→TCP→TTFB→다운로드→RTT를
한 세트로 반복하는 방식을 우선 검토한다. 이렇게 하면 특정 지표만 다른 시간대의 혼잡
상태를 관찰하는 편향을 줄일 수 있다. 다운로드 자체가 다음 RTT에 영향을 주지 않도록
세트 간 휴지 시간도 실험으로 조정한다.

## 5. 구성과 데이터 흐름

```text
config/default.json
        │
        ▼
 config validation
        │
        ▼
 measurement orchestrator ──► DNS/TCP/HTTP/Download/Ping measurers
        │
        ▼
 RunResult + MetricResult + StatisticalSummary
        │
        ├──► rule-based analyzer
        ├──► JSON history
        └──► FastAPI ──► web dashboard
```

측정기는 사실만 수집하고, 분석기는 그 사실을 해석한다. 화면은 임계값을 자체 계산하지
않고 분석기가 반환한 근거와 설명을 표시한다. 이 분리는 규칙 변경이 측정 코드나 UI에
영향을 주는 일을 줄인다.

## 6. 결과 계약

모든 실행은 `RunResult` 하나를 생성한다.

```json
{
  "schema_version": "1.0",
  "run_id": "uuid",
  "mode": "measured",
  "target_name": "Example target",
  "target_host": "example.com",
  "repetitions_requested": 5,
  "started_at": "ISO-8601 UTC timestamp",
  "finished_at": "ISO-8601 UTC timestamp",
  "metrics": [
    {
      "key": "dns_ms",
      "label": "DNS",
      "unit": "ms",
      "samples": [12.1, 12.4, 11.9, 13.0, 12.2],
      "status": "success",
      "error": null,
      "summary": {
        "count": 5,
        "mean": 12.32,
        "median": 12.2,
        "minimum": 11.9,
        "maximum": 13.0,
        "standard_deviation": 0.37
      }
    }
  ],
  "notes": []
}
```

`schema_version`을 두어 향후 데이터 형식이 바뀌어도 과거 측정 기록을 구분할 수 있게
한다. `mode=demo`인 데이터는 실제 측정과 혼동하지 않도록 UI와 CLI에서 명시한다.

## 7. 목표 서버 정책

하나의 서버 결과는 사용자의 전체 인터넷 품질을 완전히 대표하지 않는다. 2주차에는
다음 원칙으로 대상을 선정한다.

- 국내 또는 가까운 기준 서버와 원거리 비교 서버를 구분한다.
- 다운로드는 크기와 캐시 정책을 통제할 수 있는 허가된 파일만 사용한다.
- 리다이렉션과 CDN 선택 결과를 기록한다.
- 동일 대상에 과도한 부하가 가지 않도록 반복 횟수와 파일 크기를 제한한다.
- 대상 서버의 자체 처리 지연 또는 속도 제한이 결과에 개입할 수 있음을 표시한다.

## 8. 윤리와 개인정보

- 본인 소유 또는 명시적으로 측정을 허용한 네트워크와 서버만 사용한다.
- 학교 인프라나 제3자 서비스에 부하 시험을 수행하지 않는다.
- 패킷 감청, 다른 사용자의 트래픽 캡처, 개인정보 수집 기능을 포함하지 않는다.
- 저장 결과에는 대상, 시각, 측정값만 두고 URL의 민감한 쿼리나 인증 정보를 남기지 않는다.

## 9. 1주차 완료 조건

- 기본 설정을 읽고 잘못된 설정을 사용자에게 설명할 수 있다.
- `python -m netdoctor plan`이 실제 요청 없이 측정 계획을 출력한다.
- `python -m netdoctor demo --json`이 고정된 결과 계약을 출력한다.
- `python -m netdoctor dashboard`로 UI 초안을 확인할 수 있다.
- 표본 통계와 설정 검증 테스트가 통과한다.
