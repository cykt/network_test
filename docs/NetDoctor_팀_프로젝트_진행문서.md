# [컴퓨터 네트워크] NetDoctor 4인 팀 프로젝트 진행 관리 문서

> **프로젝트 목표**: DNS 조회, TCP 연결, TTFB, 다운로드 처리율, RTT를 측정하고, 결과를 이해하기 쉬운 네트워크 진단으로 제공하는 웹 애플리케이션 완성
> **운영 원칙**: 각 담당자는 자기 브랜치에서 작업하고 매주 말 통합한다. 측정 결과와 진단에는 관측 근거를 표시하며, 본인이 통제하거나 측정을 허용한 서버만 사용한다.

## 📅 2. 주차별 실행 계획 및 체크리스트 (Week 10 ~ Week 14)

### [Week 10] 설계 확인과 개발 준비
* **주간 목표**: 기존 1주차 골격을 점검하고 실제 측정 개발에 들어갈 공통 기준(인터페이스)을 확정한다.
* **담당별 세부 작업**:
  - [ ] **A (측정 엔진)**: 저장소/설정 구조 확인, 5개 측정 함수의 입출력·타임아웃 설계, DNS 결과 IP를 TCP에 전달하는 경계 확정
  - [ ] **B (통계·진단)**: JSON 스키마와 대표 통계 확정, 단일/조합 진단 기준 초안 작성, 중앙값을 우선할 상황 정리
  - [ ] **C (대시보드)**: 기존 와이어프레임 실행 확인, 대상·반복 횟수·타임아웃 입력 화면 점검, 임시 JSON 표시 컴포넌트 설계
  - [ ] **D (검증·통합)**: Git 브랜치/커밋 규칙 설정, 기존 단위 테스트 실행, 실패/타임아웃 테스트 목록 작성
* **공동 점검**: 네 명이 동일한 실행 환경에서 `python -m netdoctor demo` 및 `dashboard`를 실행하고, 브랜치 생성 및 작업 인터페이스를 합의한다.
* **완료 기준**: 측정 항목·JSON 형식·역할·브랜치가 확정되고 11주차 구현을 바로 시작할 수 있다.

---

### [Week 11] 측정 엔진 구현
* **주간 목표**: 실제 측정값, 원본 표본, 요약 통계를 CLI와 JSON으로 출력한다.
* **담당별 세부 작업**:
  - [ ] **A (측정 엔진)**: DNS·TCP·TTFB·다운로드·ping 함수 구현, 5~10회 반복과 타임아웃 처리, 부분 실패가 전체 실행을 중단하지 않도록 구현
  - [ ] **B (통계·진단)**: 평균·중앙값·최소·최대·표준편차 계산, 패킷 손실률 계산, 측정 결과를 요약하는 모듈 작성
  - [ ] **C (대시보드)**: 측정 API 입출력 구조 준비, 임시 JSON 수치 카드와 표 구성, 로딩·오류 상태 화면 구현
  - [ ] **D (검증·통합)**: DNS 실패·타임아웃·ICMP 차단 테스트 케이스 작성, 코드 리뷰와 브랜치 통합, 실행 예시와 결과 캡처 기록
* **공동 점검**: A의 측정 JSON을 B와 C가 동시에 사용해 데이터 형식 오류를 확인하고, D가 실패 상황을 재현한다.
* **완료 기준**: CLI에서 실제 측정값과 요약 통계가 출력되며 일부 실패도 측정 불가로 안전하게 처리된다.

---

### [Week 12] 설명 가능한 분석 구현
* **주간 목표**: 숫자를 원인 가능성과 서비스별 사용 적합도 설명으로 변환한다.
* **담당별 세부 작업**:
  - [ ] **A (측정 엔진)**: 누락/실패 상태를 표준화, 분석 엔진이 사용할 안정적 JSON 제공, 재현 가능한 샘플 결과 준비
  - [ ] **B (통계·진단)**: 단일/조합 규칙 구현, 웹·1080p/4K·화상회의 평가, 근거와 불확실성 문구 포함
  - [ ] **C (대시보드)**: 종합 등급·병목·별점 표시, 상세 진단 설명 구현, 성공·부분 성공·불가 상태 구분
  - [ ] **D (검증·통합)**: 고정 테스트 시나리오 작성, 기대 vs 실제 진단 비교, 규칙표와 예시 결과 문서화
* **공동 점검**: 샘플 결과별로 진단 규칙과 화면 문구를 함께 검토해 과도한 단정 표현을 제거한다.
* **완료 기준**: 고정 시나리오에서 진단, 관측 근거, 불확실성 문구가 함께 반환된다.

### [Week 13] 웹 대시보드 연결
* **주간 목표**: 브라우저에서 진단 시작부터 결과 설명까지 한 흐름으로 완료한다.
* **담당별 세부 작업**:
  - [ ] **A (측정 엔진)**: FastAPI 측정 API 연결, 진행/부분 실패 상태 반환, 그래프용 반복 결과 제공
  - [ ] **B (통계·진단)**: API 입출력 검토, 대시보드용 평가 문구 정리, 이전·현재 비교 데이터 정의
  - [ ] **C (대시보드)**: 진단 시작/진행 표시, 수치 카드·그래프·설명 완성, 이전 결과 비교 구현
  - [ ] **D (검증·통합)**: 브라우저 전체 흐름 테스트, 오류/부분 성공 화면 확인, 버그 우선순위 관리
* **공동 점검**: 브라우저에서 같은 입력으로 반복 실행하며 측정·분석·표시 간 데이터 연결을 점검한다.
* **완료 기준**: 대상과 반복 횟수 입력 후 측정, 분석, 결과 표시까지 브라우저에서 완료된다.

### [Week 14] 환경별 검증과 발표 완성
* **주간 목표**: 재현 가능한 실험 근거를 확보하고 최종 결과물을 완성한다.
* **담당별 세부 작업**:
  - [ ] **A (측정 엔진)**: 유선/Wi-Fi, 유휴/부하, 근거리/원거리 측정, OS별 ping 차이와 ICMP 차단 확인, 측정 안정성 점검
  - [ ] **B (통계·진단)**: 임계값·별점 조정, 부하 전후 RTT 비교, 오진 가능성과 한계 검토
  - [ ] **C (대시보드)**: 최종 화면 오류 수정, 대표 시연 시나리오 구성, 시연 캡처 정리
  - [ ] **D (검증·통합)**: 환경별 비교표 작성, README·구성도·순서도 작성, 보고서·발표 자료 완성
* **공동 점검**: 새 기능은 추가하지 않고, 환경별 실험 결과·재현 절차·발표 흐름을 한 번에 점검한다.
* **완료 기준**: 실행 가능한 프로그램, 소스, README, 실험표, 보고서, 구성도, 발표 자료가 완성된다.
