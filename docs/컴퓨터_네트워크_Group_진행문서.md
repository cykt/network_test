## 프로젝트 개요

**NetDoctor: Explainable Network Quality Diagnostics with an Upstage Solar Agent**

### Problem (문제 정의)
기존 네트워크 속도 측정 서비스는 단순 최종 다운로드/업로드 대역폭(Mbps)만을 단편적으로 제공합니다. 그러나 사용자가 인터넷이 느리다고 체감할 때 실제 원인은 네임서버 조회 지연(DNS), 전송 계층 핸드셰이크 지연(TCP), 백엔드 서버 처리 지연(TTFB), 물리적 전파/큐잉 지연(RTT) 등 다양한 네트워크 계층에 분산되어 있습니다. 또한 일반 사용자는 복잡한 밀리초(ms) 지연 수치를 보고는 본인의 회선으로 화상회의나 4K 스트리밍이 원활할지 직관적으로 판단하기 어렵습니다.

### 필수 세 조건 충족 확인 (수업 필수 요건)
1. **네트워크 개념 적용 (조건 1)**: 응용 계층(DNS), 전송 계층(TCP 3-Way Handshake 순수 수립), HTTP 프로토콜(TTFB - 첫 바이트 응답 지연), 네트워크 계층(ICMP Ping RTT 및 패킷 손실률), 종단 간 실제 처리율(Throughput)을 계층별로 독립 격리하여 측정합니다.
2. **LLM 에이전트 적용 (조건 2)**: 에이전트가 측정 엔진의 정량적 지표(JSON)를 도구 호출(Tool Calling)로 조회하고, 사용자의 자연어 질문(예: '지금 줌 화상회의 50명 접속 시 끊김 없을까?')에 대해 관측 수치를 근거로 원인과 해결책을 설명합니다. *(에이전트가 없으면 손으로 해야 할 일: 사용자가 5개 지표의 밀리초 값을 직접 수집하고 전공 서적과 임계치 표를 대조해 수작업으로 계산해야 함)*
3. **모델은 Upstage Solar 사용 (조건 3)**: Upstage Solar API(solar-pro / solar-mini)를 채택하며, Tool Calling 기능을 통해 NetDoctor 측정 데이터 및 진단 룰과 결합됩니다.

### Method & Deliverables (방법론 및 산출물)
- **조작적 정의 기반 독립 측정**: DNS(socket.getaddrinfo), TCP(connect), TTFB(urllib), RTT(subprocess ping), 다운로드 처리율
- **통계적 안정성**: 5~10회 반복 측정 및 중앙값(Median), 표준편차 산출, 부분 실패 격리
- **Upstage Solar 에이전트 연동**: diagnose_network(), get_metric_summary() 도구 호출 루프 구성
- **최종 산출물**: 측정 엔진(engine.py), 분석 모듈(analyzer.py), Solar 에이전트(agent.py), 웹 대시보드(web/), 통합 테스트 및 환경별 비교 실험 보고서
