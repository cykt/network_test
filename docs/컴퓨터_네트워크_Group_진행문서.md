## 프로젝트 개요

**NetDoctor: Explainable Network Quality Diagnostics Web Application**

### Problem (문제 정의)
기존의 네트워크 속도 측정 서비스(예: Speedtest, Fast.com 등)는 주로 단순한 최종 다운로드/업로드 대역폭(Mbps) 수치만을 단편적으로 제공합니다. 그러나 사용자가 인터넷이 느리다고 체감할 때, 실제 원인은 네임서버 조회 지연(DNS), 전송 계층 핸드셰이크 지연(TCP), 백엔드 서버 처리 지연(TTFB), 물리적 전파/큐잉 지연(RTT) 등 다양한 네트워크 계층에 분산되어 있습니다. 또한, 전문 지식이 없는 일반 사용자는 복잡한 밀리초(ms) 수치만 보고는 본인의 회선으로 화상회의나 4K 스트리밍이 원활할지 직관적으로 알기 어렵습니다.

### Objective (프로젝트 목표)
NetDoctor는 DNS 조회, TCP 연결, HTTP TTFB, 다운로드 처리율, ICMP Ping RTT를 독립적으로 격리 측정하고, 그 관측값의 조합을 바탕으로 병목 구간을 자동 판정하여 일반 사용자가 이해하기 쉬운 자연어 진단 리포트와 서비스별 적합도(웹/스트리밍/화상회의)를 제공하는 반응형 웹 대시보드를 완성합니다.

### Method (측정 및 분석 방법)
1. **5대 지표 독립적 격리 측정**:
   - **DNS (`dns_ms`)**: `socket.getaddrinfo()`를 호출하여 도메인을 IP로 해석하는 순수 시간 측정
   - **TCP 연결 (`tcp_ms`)**: DNS 해석 시간을 배제하기 위해 미리 확인한 IP 주소로 직접 `connect()`를 수행하여 순수 3-Way Handshake 시간 측정
   - **TTFB (`ttfb_ms`)**: TCP 연결 후 HTTP GET 요청을 전송하고 첫 응답 바이트를 수신하기까지의 시간 측정 (서버 처리 지연 격리)
   - **다운로드 처리율 (`download_mbps`)**: 응답 본문 비트 수를 순수 전송 시간으로 나눈 실제 종단 간 처리율 측정
   - **RTT (`rtt_ms`)**: OS 표준 ICMP ping을 활용한 왕복 전파/큐잉 지연 및 패킷 손실률 측정
2. **반복 정책 및 통계 처리**:
   - 각 지표별 5~10회 반복 측정하여 순간적 스파이크 이상치에 강건한 **중앙값(Median)**과 변동성(표준편차) 산출
   - 특정 지표 실패(예: ICMP 차단 등)가 전체 측정을 중단시키지 않도록 **부분 실패 격리(Fault Isolation)** 적용
3. **규칙 기반 설명 가능 진단 (Explainable Diagnosis)**:
   - 각 계층별 임계값을 기반으로 병목 원인 도출 및 웹 브라우징, 1080p FHD, 4K UHD, 실시간 화상회의 사용 적합도(별점) 자동 판정
   - 관측 근거와 함께 네트워크 측정의 한계를 밝히는 불확실성 안내 문구 부착

### Deliverables (최종 산출물)
- 재현 가능한 네트워크 5대 지표 측정 및 통계 처리 엔진 (`netdoctor/engine.py`, `models.py`)
- 규칙 기반 병목 분석 및 서비스 적합도 평가 모듈 (`netdoctor/analyzer.py`)
- FastAPI 기반 비동기 측정 API 및 실시간 반응형 대시보드 (`netdoctor/web/index.html`)
- 환경별(유선 LAN vs Wi-Fi vs 모바일 핫스팟, 유휴 vs 부하) 비교 실험 데이터셋 및 검증 테스트 (`tests/`)
- 최종 보고서, 시스템 아키텍처 구성도 및 발표 장표

### 예상 질문과 답
- **질문 1**: TCP 연결 시간과 TTFB를 왜 분리해서 측정해야 하나요?
  - **답변**: TCP 연결 시간은 순수 네트워크 왕복 및 전송 계층 3-Way Handshake 성능을 나타내며, TTFB는 서버가 요청을 받아 백엔드 연산을 처리하는 시간(서버 부하)을 반영하므로 두 구간의 병목을 독립적으로 판별하기 위함입니다.
- **질문 2**: 왜 평균(Mean) 대신 중앙값(Median)을 대표값으로 채택했나요?
  - **답변**: 무선 네트워크 환경에서는 순간적인 전파 간섭이나 OS 프로세스 스케줄링으로 인해 1~2개의 심한 스파이크 이상치(Outlier)가 발생할 수 있습니다. 중앙값은 이러한 이상치에 왜곡되지 않고 실제 사용자의 일반적인 체감 성능을 가장 신뢰성 있게 대변합니다.
